## Notes

- Seems like there are way to many false positives from refactoring miner, to naively perform v2-r. It may be more interesting to identify from underlying refactorings - such as extract class, extract interface, extract method and then reverse specifically those. For example, if there is an extract-class in a commit, we should reverse that and only that. Because it is the high level change that drives all the other changes.
- **Most** commits seem to capture one granular change - with one motivating reason. This is a great.
- Seems like there could be a simple way to mine for *refactoring* commits, some of which aren't detected by rminer.

## Benchmark

The benchmark is a series of challenges for a refactoring sytem. The challenges can be any one of:

1. Here is a file. Refactor it. (there is no additional context. Refactorings improve design, code quality.)
2. Get rid of \_these_ \'issues' generated by static analysis tools, such as PMD, SonarQube
3. Here's a file. Refactor it given an intent (deprecate a method. perform a type change [Time->Duration]. etc.)

The intent of the refactoring change is the most important thing that guides the list of changes.
